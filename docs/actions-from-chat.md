# Как запускать проверки GitHub Actions из чата

Репозиторий: `serozh98/tos`. Для создания **нового запуска** через подключённый GitHub из чата прямого `workflow_dispatch` нет.

## Событийный запуск
1. Создать рабочую ветку и pull request к `main`.
2. Через GitHub Contents API обновить содержательный файл **в ветке PR** (с использованием текущего SHA файла).
3. Новый commit обновляет HEAD PR и создаёт событие `pull_request: synchronize`.
4. Workflow с `on: pull_request` запускается автоматически.
5. Получить SHA, найти привязанный запуск, прочитать jobs, steps, logs и артефакты.
6. При ошибке внести исправление следующим commit: новый `synchronize`, новый запуск.

При открытии нового PR срабатывает `pull_request: opened`, что тоже подходит для первой проверки.

## Проверка оглавления Shuhaige 360588

- На PR выполняются тесты, а затем **только проверка оглавления**: без `--save-text`, без сохранения полных RAW-глав.
- Вывод: `out/shuhaige-360588/manifest.json` и `summary.md`, доступные в артефакте GitHub Actions.
- Результаты `CATALOG_ONLY`, `CATALOG_ERROR`, `BLOCKED` описывают фактическое состояние проверки, а не перевод.
- Для получения полного RAW требуется отдельный ручной `workflow_dispatch` и подтверждение прав.
- Не отключать ограничения по `robots.txt`, не обходить капчу, платную защиту, авторизацию и иные запреты.

## Повтор существующего запуска

Если запуск уже существует и требуется повторить неудавшиеся задания, возможны методы GitHub Actions API: повторить все упавшие jobs или конкретный job. Это **повтор**, а не создание нового workflow run через новый commit.

## Ограничения

- Изменения сначала в PR, не в `main`; объединять их после проверки.
- Для исправления ошибок менять код по существу, а не создавать пустые commit.
- Успешный запуск тестов не гарантирует доступность стороннего сайта.
- GitHub Action, сохранивший результаты, не переводит главы и не обновляет карточки Notion автоматически.
